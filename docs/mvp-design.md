## 1. プロジェクト概要

### 1.1 ビジョン
**「正解を覚える」のではなく、「解き方を自分で発見する」ゲーム。** 産業機械が動く世界で、プレイヤーが観察・仮説・実験・一般化を繰り返し、競技プログラミングの考察力を鍛える。

### 1.2 プロダクト原則
1. **課題が先、用語が後**：アルゴリズム名や最適解を最初に提示しない。
2. **機械は初めから存在**：搬送・整列・検品などの工場設備を初回プレイで体験させる。
3. **結果ではなく根拠を重視**：偶然正解の箱を選んだだけではクリアとしない。
4. **失敗から改善できる**：試行履歴、候補範囲、やり直しを明確にする。
5. **学習と遊びを接続**：将来は発見した手順をコード化し、生産設備を自動化する。

### 1.3 対象ユーザー
- 主対象：プログラミング初心者〜競プロ初中級者。典型解法を暗記するだけでなく、着眼点を身に付けたい人。
- MVPの利用環境：PCブラウザを優先。タブレット・スマートフォンは表示崩れを防ぐが、最適化は後続。

### 1.4 MVPの検証仮説
- H1：説明を読ませる前に試行錯誤を促すと、プレイヤーが「整列情報を使い探索範囲を絞る」考え方を発見できる。
- H2：工場設備とスキャン演出により、単独の問題演習よりも再挑戦したくなる。
- H3：2回目の挑戦では、スキャン回数または「候補の絞り込み」に関する説明が改善する。

**初期検証の目安**：5〜10人の観察テストで、(a) 無誘導で開始できた人数、(b) クリア率、(c) 2回目の探索回数、(d) 自分の言葉で根拠を説明できた人数、(e) もう1ステージ遊びたいと思うかを記録する。小標本のため数値を製品全体の学習効果と断定しない。

## 2. MVPのスコープ

### 2.1 実装対象（P0）
- 2D工場画面、機械の視覚表現（搬送ベルト、整列機、スキャナー、出荷ゲート）。
- **探索ステージ1本**：16個の整列済みコンテナから、品質70以上となる最初の位置を特定する。
- コンテナ選択→スキャン→結果表示→候補範囲更新→成功/失敗判定。
- 5回以内のスキャン制約、リトライ、ゲーム内ヒント、結果・考察表示。
- FastAPIでの挑戦セッション管理とサーバー側判定。
- Supabase Authの匿名サインインと、PostgreSQLへの進捗保存。
- 基本的な操作ログとエラー表示、ユニットテスト。

### 2.2 後続開発（P1以降）
- 操作履歴の再生、次の探索ステージ、探索範囲の可視化強化。
- 命令列の編集・実行、条件分岐・ループ、コードエディタ（段階導入）。
- 工場設備の配置・自由自動化、複数ロボット、資源経済。
- 2.5D/3D描画（React Three Fiber）、BFS/DP/累積和などの教材追加。
- Pythonの自由実行、ランキング、対戦、AIチューター。

**非目標**：MVPでは『農家は Replace() されました』相当の自由な生産シミュレーターを作らない。まず「考察の面白さ」と「工場の世界観」が成立するか検証する。

## 3. ステージ仕様：ST-001「鉱石の検品ライン」

### 3.1 目的・物語
自動整列機によって**品質の低い順に**並べられた16個の鉱石コンテナが搬送されている。検品スキャナーで一部の品質を調べ、**品質70以上となる最初のコンテナ**を確定させ、出荷ゲートへ指示する。

### 3.2 工場設備と機能
| 設備 | 視覚・操作 | 学習上の意味 |
|---|---|---|
| 搬送ベルト | コンテナが順序を保って配置される | 添字と順序の概念 |
| 自動整列機 | 「左から品質の昇順」を表示 | 探索に使える前提条件 |
| 検品スキャナー | プレイヤーが選択した1箱の品質を表示 | 問い合わせのコスト |
| 出荷ゲート | 正解が確定すると自動で開く | 解法の成立と達成感 |

### 3.3 ルール（MVPで固定）
- コンテナ数：16。画面表示は1〜16番、内部添字は0〜15。
- 品質：昇順。実値は未検品の箱について表示しない。
- 閾値：70。品質70以上のコンテナが**少なくとも1個存在する**ことを保証する。
- スキャン回数上限：5回。各スキャンは1回として計上し、同じ箱の重複スキャンはUIで防止する。
- スキャンした品質値に基づいて正解候補範囲 `[lo, hi]`（両端含む）を更新する。
- **クリア条件**：候補範囲が1箱に確定する（`lo === hi`）。箱を運任せで当てただけでは成功にしない。
- 5回終了時に候補が2つ以上残る場合は失敗。再挑戦可能。
- やり直すたびに品質配列を再生成し、答えの位置も変える。単なる位置暗記を防ぐ。

### 3.4 候補範囲の更新規則（サーバー側の正）
初期値 `lo=0`, `hi=15`。選択添字 `i` の品質が `v` のとき：
- `v < 70`：`lo = max(lo, i + 1)`（選択位置以前はすべて不適格）。
- `v >= 70`：`hi = min(hi, i)`（選択位置より右に最初の適格品はない）。
- `lo === hi` なら**解を論理的に一意確定**。`lo > hi` はデータ・実装不整合としてエラー。

この判定は「整列済み」「適格品が必ずある」の2つの保証に依存する。プレイ後の解説でその前提を振り返る。

**開発用固定データ例**（ユーザーには全値を配信しない）：`[8,15,20,24,31,37,42,46,51,58,63,68,72,76,83,91]`。正解は内部添字12（画面では13番）。二分探索に沿った4回以内のスキャンで確定できる。

### 3.5 プレイフロー
1. 工場へ到着。整列機が稼働し、目標「品質70以上の最初の箱」が表示される。
2. プレイヤーが箱を選択しスキャン。スキャナーが作動し品質が明らかになる。
3. 候補範囲が縮小し、スキャン残数が減る。必要なら再度スキャン。
4. 候補が1つに確定：ゲートが開く→結果画面で手順・回数・根拠を振り返る。
5. 回数を使い切る：失敗画面で「どこまで絞れたか」を表示→リトライ。

### 3.6 ヒントの段階
- H0：開始時「左から品質が低い順」とだけ明示。
- H1：詰まった場合「1回調べると、どちら側を調べなくてよくなる？」。
- H2：再挑戦後「候補範囲をなるべく半分にできる箱は？」。
- H3：クリア後に「二分探索／境界を見つける探索」とその成立条件を説明。

最初から「真ん中を選べ」を強制しない。短いプレイ時間でも自由に実験できるようにする。

## 4. UI・UX要件

### 4.1 画面構成
```
┌──────────────────────────────────────────────────┐
│ Brain Forge / ST-001 / 目標: 品質70以上の最初の箱 │
├──────────────────────────────────────────────────┤
│ [整列機] → [搬送ベルト：16箱] → [スキャナー] → [ゲート]│
│      ↑クリック可能な箱・検品済みの品質表示       │
├─────────────────────────┬────────────────────────┤
│ 候補範囲・スキャン残数   │ 今回の検品ログ         │
│ [現在の候補：7〜13番]   │ 8番: 46 → 右に絞る    │
├─────────────────────────┴────────────────────────┤
│ ヒント / リトライ / 結果説明                       │
└──────────────────────────────────────────────────┘
```

### 4.2 操作・アクセシビリティ
- 箱はクリックに加えキーボード選択（Tab/Enter）に対応。
- 未検品・検品済み・候補外を色だけで区別せず、枠線・アイコン・文字で区別。
- 1スキャンの演出はスキップ可能。ネットワーク待機中は二重送信を防ぐ。
- 開始までにアカウント登録画面を挟まない。初回アクセスで匿名ユーザーとして開始する。

## 6. システム設計

### 6.1 技術スタック
- Web：React + TypeScript + Vite。2D描画は初期SVG（16箱のUIを素早く検証）、必要に応じCanvasへ移行。
- API・ルール：Python + FastAPI。ステージ状態、スキャン判定、回数制限を管理。
- DB・認証：Supabase PostgreSQL + Supabase Auth（匿名サインイン）。
- 3D：React Three Fiberは将来採用。描画アダプターを置換する方針で、MVPの依存から外す。
- 配信：WebはVercel、APIはPython対応ホスティング、DBはSupabase。

### 6.2 責務分離
```
React UI ─→ Game Controller ─→ FastAPI / Attempt Service
  │                 │                    │
  └── 2D Renderer ←─┴── 検証済み状態 ─────┘
                                          │
                                 Supabase PostgreSQL
                                 ├─ private.stage_attempts
                                 └─ public.stage_progress
```
- フロント：画面・アニメーション・選択入力・API応答の描画のみ。未公開の品質配列を保持しない。
- バック：品質配列生成、ルール評価、ログ、成否、進捗確定。表示に依存しない。
- 各スキャンは低頻度の**イベント通信**。毎フレーム通信しないためWebゲームの操作感を維持しやすい。
- 将来は `GameViewState` に対して2D/3D Rendererを差し替え、工場のロジックは維持する。
- TypeScriptとPythonで判定ロジックを二重管理しない。サーバーがルールの唯一の正となる。

### 6.3 リポジトリ案
```
brain-forge/
├── apps/
│   ├── web/              # React UI・2D Renderer
│   └── api/              # FastAPI・ステージロジック
├── packages/
│   └── contracts/        # OpenAPI由来の型・APIクライアント
├── supabase/
│   └── migrations/
├── docs/
│   └── mvp-design.md
└── README.md
```

## 7. API仕様案
すべてJSON。スキーマはFastAPI OpenAPIからWeb用TypeScript型を生成する。認証必要な操作ではSupabase JWTをBearerトークンとして送信する。

| Method | Path | 役割 |
|---|---|---|
| GET | `/api/v1/stages/ST-001` | 公開ステージ説明・設備・制約を返す |
| POST | `/api/v1/attempts` | 新しい挑戦を作成（匿名認証も可） |
| POST | `/api/v1/attempts/{id}/scans` | 1箱検品しサーバーで候補範囲を更新 |
| GET | `/api/v1/attempts/{id}` | 自分の挑戦状態を取得・画面復帰 |
| GET | `/api/v1/me/progress` | 自分のベスト記録を取得 |

**スキャン要求例**
```json
{"index": 7, "action_id": "UUID", "expected_step": 0}
```

**スキャン応答例**（開発用データにおける7番目の0-based箱）
```json
{
  "index": 7,
  "quality": 46,
  "candidate_range": {"lo": 8, "hi": 15},
  "scans_used": 1,
  "scans_remaining": 4,
  "status": "in_progress"
}
```

- `action_id` によって通信再送による重複スキャンを防止する。
- `expected_step` 不一致は409 Conflict、回数超過・終了済み操作は422、他人の挑戦IDは404/403。
- 生成された品質配列・正解位置はAPIから事前に返さない。終了後の解説として公開する範囲は別途制御する。

## 8. DB設計案

### 8.1 テーブル
| スキーマ.テーブル | 主要カラム | 意図 |
|---|---|---|
| `private.stage_attempts` | `id`, `user_id`, `stage_key`, `stage_version`, `qualities` (JSONB), `lo`, `hi`, `scans_used`, `events` (JSONB), `status`, `started_at`, `finished_at` | 正解を含む挑戦データ。**APIサーバーのみアクセス** |
| `public.stage_progress` | `user_id`, `stage_key`, `best_scans`, `clear_count`, `updated_at` | ユーザーが閲覧できる進捗。複合PK `(user_id, stage_key)` |

ステージの表示文言・制約・機械設定は、MVPではリポジトリ内の**バージョン付き定義ファイル**で管理する。DBのステージ編集機能は不要。

### 8.2 認証・アクセス制御
- Supabaseの匿名サインインを使用。匿名ユーザーも固有の `auth.uid()` を持つが、ブラウザデータ消去・ログアウト後には同一進捗へ復帰できない。後続でGoogle等とのアカウント連携を検討する。
- `public` で公開する全テーブルにRLSを有効化。`stage_progress` のSELECTは `auth.uid() = user_id` のみ許可。
- 進捗のINSERT/UPDATEは**APIサーバーのみ**。フロントから自由にベスト記録を書けないようにする。
- `private.stage_attempts` はData APIへ公開しない。DBのシークレットキーはサーバーにのみ配置し、フロントへ送らない。
- APIはJWT署名・発行元等を検証し、挑戦の `user_id` がリクエスト本人と一致することを必ず確認する。
- スキャナAPIへの回数・頻度制限、入力検証、ログ記録を設定する。

| NFR-06 | 拡張性 | 2Dの表示を変えてもサーバー側ルール・データに変更不要 |
| NFR-07 | アクセシビリティ | キーボード操作、非色依存の状態表示、可読なテキスト |

## 10. テスト設計

### 10.1 ゲームルール
- 正解が先頭・中央・末尾にある場合でも、正しく絞り込める。
- 順序が昇順でない入力、適格品が1つもない入力を生成しない。
- 境界を1つずつ確認する方法／二分探索方法の双方がルール通りに評価される。
- 16箱で中央を選び続ければ**4回以内**で候補が一意確定する。
- 同じ箱の重複、無効な添字、5回超過、終了後スキャンを拒否する。

### 10.2 API・DB
- 2重リクエストでスキャン回数が増えない。
- 他人の挑戦IDで検品・状態取得できない。
- `stage_progress` のRLSで他人の行が取得できない。
- 通信切断後の再取得で直前のサーバー状態に復帰する。
- 成功時のみ進捗が確定し、ベストスキャン数は悪化しない。

### 10.3 UX
- 少なくとも5人に初回プレイを観察してもらい、説明の読まれ方・迷った操作・考え方の変化をメモする。
- クリア後に「なぜ全部スキャンする必要がなかったか」を自分の言葉で説明してもらう。

### MVPリリース判定（Definition of Done）
- [ ] 初めて来た人が登録フォームなしでプレイを開始できる。
- [ ] 初回から機械が存在し、工場内でスキャンという行動を行える。
- [ ] 16箱・品質70以上の最初の位置を、5回以内のスキャンで論理的に特定できる。
- [ ] 偶然の回答だけではクリアできず、候補を一意に絞る必要がある。
- [ ] 失敗、リトライ、成功、考察の振り返りが機能する。
- [ ] バックエンド側で判定され、Supabaseに進捗が正しく保存される。
- [ ] ユニット・API・RLSの主要テストに合格する。
- [ ] 少人数の実プレイ結果を記録し、次の改善施策を決められる。

## 12. リスクと設計判断

| リスク | 対策 |
|---|---|
| 工業要素が単なる背景になる | 整列機が「昇順」を保証し、スキャナーが検査コストを生むなど、設備をルールに直結させる |
| 二分探索の手順を暗記するだけになる | 挑戦ごとに品質・正解位置を変更、クリア後に前提条件を言語化する |
| 当てずっぽうで成功できる | 正解の一意確定（候補範囲 `[lo,hi]` が1点）を必須とする |
| API応答がゲーム体験を妨げる | スキャン演出を先行表示、通信中表示、再送の冪等性を実装 |
| 将来の3D化で作り直し | 描画とルールを分離、ビュー用DTOに機械・箱の位置を持たせる |
| Supabaseの権限不備 | private schema、RLS、鍵の分離、他ユーザーテストを必須にする |
| スコープ膨張 | P0＝ST-001の完走に固定。自由自動化・コード入力・3DはP1以降 |

## 13. 今回の決定と次のレビュー項目

**今回の決定**：Web中心／初期2D・将来R3F／React+TS／FastAPI／Supabase／機械が最初から登場／最初の教材は探索／コード入力は段階的に解放。

**次のレビューで決める**：工場のアートスタイル、スキャナー演出、ヒント表示の強さ、ステージ1の対象難易度、匿名プレイの継続・アカウント連携方針。
